# The GameMaker project format, and how to add rooms, objects and scripts by editing text

All facts from the official manual, checked 2026-10-19:
https://manual.gamemaker.io/monthly/en/Additional_Information/Project_Format.htm

## What the manual states

- At the project root there is one project file with the .yyp extension. It describes the resources in the project
  and the project metadata.
- Next to it is a .resource_order file which stores the order of groups and assets in the Asset Browser when the
  filter is set to Custom Order. GameMaker adds it to .gitignore by default when "Add skeleton .git defaults" is
  enabled, because it is a per user ordering preference.
- Resource files have the .yy extension. They store the information for one asset, and any other files belonging to
  that asset (scripts, shaders, images, audio). The data is stored in a JSON-like format.
- A .yy resource whose associated files are missing (for example a sprite .yy with no PNG) is reported in the Project
  Health window when the project opens.
- .gitignore and .gitattributes are added to new projects when the same setting is on. The default .gitattributes
  marks .yy files as linguist-generated so hosts do not misidentify the language.
- A .yyz is a compressed project export, made with Export Project > YYZ. Marketplace packages are .yymps (2.3+),
  .yymp (pre 2.3) and .gmez (1.x), and older project files are .gmx.
- If a project fails to load because resources are missing, the IDE offers to unlink resources so it can open; the
  manual states plainly that this is not a replacement for source control and is not a fix for a broken project.
- The Project Tool (https://manual.gamemaker.io/monthly/en/IDE_Tools/Project_Tool.htm, checked 2026-10-19) is the
  documented route for project compatibility problems.

## What the manual does NOT state, and what we therefore do

The manual does not publish a field by field schema for .yyp or .yy files. Any blog or forum post that lists the keys
is community knowledge, not a contract, and it drifts between GameMaker versions. Our rule follows from that:

1. Until a real GameMaker-generated project exists on this PC, we write the smallest possible files and treat every
   hand-written key as UNVERIFIED.
2. The first time Nayil opens our project in GameMaker, we immediately create one throwaway room, one object and one
   script inside the IDE, then diff those files against ours. Whatever the IDE wrote is the reference schema; our
   files get corrected to match it, and this document gets a "verified against IDE version X" note with the date.
3. We never invent a field. If we do not know a field, the asset is added inside the IDE once and the shape is
   copied from what the IDE produced.
4. Nothing in game code depends on a .yy field. Game logic reads data files, so a .yy correction is a build fix, not a
   code change.

## Safe editing procedure (every time)

1. Copy the file to <name>.bak-<date>-<tag> before editing. Backup naming matches the fleet convention.
2. Validate the result as JSON before saving the edit: python -c "import json,sys; json.load(open(sys.argv[1]))" <file>
   A .yy that is not valid JSON can stop the project opening, and the IDE's error is not always specific.
3. Keep resource names and any GUIDs exactly as they are. Renaming an asset by editing text leaves stale references
   in the .yyp and in every file that pointed at it; rename inside the IDE instead.
4. One resource per change. Adding a room and a script in the same edit makes a bad load ambiguous.
5. After any hand edit, open the Project Health window and read it. Missing associated files show up there.
6. Never hand edit a .yyz; it is a compressed export.

## Adding each kind of resource (the shape we will confirm against the IDE)

- Script: a folder holding one .gml file, plus a .yy describing the script resource, plus an entry in the .yyp.
  Our scripts are plain .gml with `function name(...) { ... }` bodies, no GML Visual blocks.
- Object: a folder holding a .yy and one .gml per event. Event files are named by event type and number, which is
  exactly the part we will copy from an IDE-created object rather than guess.
- Room: a folder holding exactly ONE .yy, which contains the layers, the instances and the tile data. Rooms are the
  most fragile hand edit, so they are generated by tools\gen_project.py from a small table in that script rather than
  typed by hand, and the first open in the IDE is still the proof.
- Sprite: a folder with a .yy plus PNG frames named frame-0.png upward and a layers subfolder. We generate sprites
  with our own art tooling later and import them in the IDE the first time.

## CORRECTION, 2026-10-19: verified against a real GameMaker 2024.1400 project

The study pass (knowledge\PROVENANCE.md, entry "room and object conventions across a whole game") read a real
GameMaker 2024.1400.0.911 project's files. Four things stated above or assumed earlier are now corrected, and our
generator follows the observed shape:

1. A room is ONE .yy. There are no per layer .yy files. Layers are an array inside the room .yy; instance layers carry
   their instances inline, tile layers carry a tile serialisation blob. This file previously said one .yy per layer,
   which would have produced a project the IDE cannot open.
2. .yy and .yyp files are JSON WITH TRAILING COMMAS and per kind version tags ("$GMObject", "$GMRoom", "$GMScript",
   "$GMMainOptions", "$GMRInstance"). GameMaker reads strict JSON as well, so every file we write is strict JSON, which
   is what lets tools\check_project.py parse the project with the Python standard library.
3. Event files are named exactly: Create_0, Step_0, Step_1 (begin step), Step_2 (end step), Draw_0, Draw_64 (draw gui),
   Draw_76, Alarm_<n>, Destroy_0, CleanUp_0, Other_<n> for user events 0 to 15 as Other_10 upward, and
   Collision_<object>. Observed across 525 event files over 232 objects in that project.
4. Folder entries in the .yyp are a browser view only: a Folders array of folderPath strings. No folder .yy files exist
   on disk in that project and it loads. Our generator writes the Folders array and points each resource at a folder
   path, and creates no folder files.

Still unverified on THIS PC: that the IDE opens our project with no errors, that event files attach to the intended
event numbers, and that a room draws its layers in the intended order. Those three are open items in DEVLOG.md and are
answered the first time Nayil opens the project.

## What we can and cannot verify today

- CAN verify: the files are valid JSON, the resource list in the .yyp matches the folders on disk, every event file has
  an eventList entry and the reverse, every room instance names a real object, every Included File exists in the
  mirror, no shipped file names the study copies, and our own data checker passes (tools\check_project.py,
  tools\check_data.py, and the pytest suite in tests\).
- CANNOT verify without GameMaker installed: that the IDE opens the project with no errors, that event files are
  attached to the right event, that a room's layer order draws as expected. Every one of these goes into DEVLOG.md
  as an open item on the day the skeleton lands.
